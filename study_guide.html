Huffman File Archiver
Interview Study Guide

A deep-dive technical reference for defending every design decision in the Huffman-Coding-of-Files project — from the algorithm itself to the custom bit-packing I/O layer and the archive file format.

🎯 Executive Summary

One-sentence description

A lossless file archiver that applies Huffman Coding on raw bytes to compress any file type, paired with a Python GUI and a custom .huf binary format that safely stores the original filename and restores it exactly.

Key achievements

  • 53% compression on plain-text datasets using a canonical Huffman tree.
  • Any file type — operates on raw bytes (std::ios::binary), so .pdf, .mp4, .pptx, images all work losslessly.
  • Intelligent stored-mode fallback — when Huffman overhead would make the file larger, bytes are stored verbatim.
  • 8 KB buffered BitWriter/BitReader — batches I/O to eliminate millions of per-byte system calls.
  • Deterministic tree reconstruction — tie-breaking on smallest byte symbol ensures the same tree is built during decompression.
  • Python tkinter GUI — zero-friction archiving via file dialogs; automatically suggests the correct output filename.
  • Custom HUF1 format — self-describing archive with magic bytes, version, method flag, original size, and stored filename.

Data flow (encode): The GUI opens a file dialog and passes the chosen paths to encode.exe via subprocess.run(). The C++ main reads the file, instantiates the huffman class, calls compress(), which scans the file for byte frequencies, builds a priority-queue Huffman tree, assigns variable-length binary codes, then serialises the HUF1 header + frequency table + bit-stream through BitWriter's 8 KB buffer to the output .huf archive.

Data flow (decode): decode.exe reads the HUF1 header to determine the method (STORED or HUFFMAN). For HUFFMAN it rebuilds the identical tree from the stored frequency table, then uses BitReader to walk the tree bit-by-bit until exactly originalSize bytes have been emitted — guaranteeing a perfect lossless round-trip.

📂 File-by-File Walk-through

📄 huffman.hpp — Public Interface
📄 huffman.hpp · 64 lines

Purpose

Declares the huffman class — the single public entry point the CLI tools use. All implementation details (Node, Header, frequency table) are private, giving a clean ABI boundary.

Key Structures

  • Node — tree node holding symbol, frequency, smallestSymbol (for tie-breaking), and child pointers.
  • Header — in-memory mirror of the on-disk HUF1 header: method, originalSize, originalFilename.
C++class huffman {
private:
    struct Node {
        std::uint8_t  symbol{};
        std::uint64_t frequency{};
        std::uint16_t smallestSymbol{};  // tie-break key
        Node* left{nullptr};
        Node* right{nullptr};
        bool isLeaf() const { return left == nullptr && right == nullptr; }
    };
public:
    huffman(const std::string& in, const std::string& out = "");
    void compress();
    void decompress();
    const std::string& getRestoredFileName() const;
};

Design Rationale

  • std::unique_ptr<Node> — automatic memory management; no risk of leaking tree nodes.
  • std::array<uint64_t, 256> — stack-allocated, cache-friendly frequency table for all possible byte values.
  • Separate Header struct keeps parsing logic cohesive and testable.

Purpose

Key Feature — Smart Filename Suggestion

When restoring, the GUI reads the first 18+ bytes of the .huf archive directly in Python to extract the stored original filename and pre-fills the save dialog — without invoking the C++ decoder.

Pythondef original_filename(archive_path):
    with open(archive_path, "rb") as f:
        header = f.read(18)
        if header[:4] != b"HUF1": raise ValueError()
        fn_len = struct.unpack("<H", header[16:18])[0]
        return os.path.basename(
            f.read(fn_len).decode("utf-8", errors="replace"))

Design Rationale

  • Calling subprocess.run() with capture_output=True keeps the UI responsive and correctly surfaces C++ error messages.
  • The Python layer handles only UI concerns — all compression logic stays in C++ for performance.

⚡ Custom Bit I/O Layer

Why it was rewritten

The original implementation called output.put() (a system call) once per byte produced. For a 2 MB file compressed with Huffman, that is over 1.1 million individual write calls. Each call crosses the kernel/user-space boundary and stalls the CPU pipeline.

❌ Before — per-byte I/O
void write(const std::string& bits) {
    for (const char bit : bits) {
        buffer = (buffer << 1) | (bit == '1');
        if (++bitsInBuffer == 8)
            output.put(buffer); // system call!
    }
}
// No padding count. Data lost if
// finish() is forgotten.
✔ After — 8 KB buffered
void writeBit(bool bit) {
    bitAccum_ = (bitAccum_ << 1) | (bit ? 1 : 0);
    if (++bitsInAccum_ == 8)
        pushByte(bitAccum_); // 8 KB buffer
}
int finish() { // returns padding count 0-7
    if (bitsInAccum_ != 0)
        pushByte(bitAccum_ <<= 8 - bitsInAccum_);
    flushBuffer(); // one bulk write
    return paddingBits_;
}

🌳 Compression Algorithm Details

Huffman Coding — core idea

Huffman Coding is a lossless prefix-free variable-length encoding. Symbols that appear more frequently are assigned shorter bit strings; rare symbols get longer codes. Because no code is a prefix of another, the bit-stream can be decoded unambiguously without delimiters.

Step 1 — Frequency Collection

Pseudocodefreq[256] = {0}
for each byte b in input_file:
    freq[b] += 1
// Uses a 64 KB read buffer per pass for I/O efficiency

Step 2 — Tree Building (Priority Queue)

Pseudocodemin_heap = empty priority queue
for each byte b where freq[b] > 0:
    heap.push(LeafNode(b, freq[b]))

while heap.size() > 1:
    left  = heap.pop()   // lowest frequency
    right = heap.pop()   // second lowest
    parent = InternalNode(
        frequency      = left.freq + right.freq,
        smallestSymbol = min(left.smallest, right.smallest)  // tie-break
    )
    parent.left  = left
    parent.right = right
    heap.push(parent)

root = heap.top()
ℹ️
Tie-breaking: When two nodes have equal frequency, the one with the smaller byte value is chosen first. This guarantees the tree shape is identical during compression and decompression — even though the frequency table is the only thing stored in the archive.

Step 3 — Code Generation (DFS)

Pseudocodefunction generateCodes(node, prefix):
    if node.isLeaf():
        codes[node.symbol] = prefix
        return
    generateCodes(node.left,  prefix + "0")
    generateCodes(node.right, prefix + "1")

Stored Mode Fallback

For files like JPEG, MP4, or PPTX that are already compressed, every byte appears with roughly equal frequency. Huffman generates codes of ~8 bits each — no saving. The engine detects this before encoding:

C++const std::uint64_t huffmanOverhead =
    2 + usedSymbolCount() * 9;  // 2-byte count + 9 bytes per symbol
const bool useHuffman =
    root != nullptr &&
    encodedBytes + huffmanOverhead < originalSize;

Payload — STORED method

Immediately after the header, the raw input file bytes are copied verbatim. No frequency table is written.

Payload — HUFFMAN method

Why photos, videos, and PPTX don't compress

  • JPEG / MP4: These formats apply DCT, quantisation, and entropy coding internally. Output bytes appear pseudo-random — every value 0–255 has roughly equal frequency.
  • PPTX: A PPTX file is actually a ZIP archive in disguise. Its contents are already deflated, so byte distribution is essentially uniform entropy.
  • Huffman limitation: Huffman coding only exploits symbol frequency imbalance. Adding LZ77 before Huffman — forming DEFLATE — solves this for structured data.

🚀 Enhancements & Future Work

🔀 Multi-threaded Chunk Compression

Divide large files into N equally-sized chunks, compress each in a separate std::thread, and concatenate the results.

  • Each chunk needs its own independent Huffman tree.
  • Expected speedup: ~3–4× on a quad-core for files >50 MB.
  • CV metric: "Reduced compression time by 75% via multi-threaded chunk processing."
📦 LZ77 (DEFLATE) Pre-Pass

Add a dictionary-based compressor before the Huffman stage. LZ77 scans for repeated sequences and replaces them with (offset, length) back-references. The resulting token stream is then Huffman-encoded — this is exactly the DEFLATE algorithm used by .zip, .gz, and PNG.

  • Enables meaningful compression of source code, JSON, XML, and structured binary.
  • CV metric: "Implemented DEFLATE, enabling high-ratio compression on binary formats previously resistant to entropy coding."
📁 Directory Archiving (tar-style)

Extend HUF1 to support multiple file entries. Each entry has its own sub-header (relative path, size, method) followed by its payload. The encoder recursively walks directories with std::filesystem::recursive_directory_iterator.

🕹️ GUI Improvements
  • Drag-and-drop: Accept files dragged onto the window using tkinterdnd2.
  • Progress bar: Show real-time progress by reading stdout as the C++ encoder runs.
  • Compression preview: Show estimated ratio before committing, based on a quick frequency scan.
🔐 Integrity Checksums

Append a CRC-32 or SHA-256 checksum to the archive. The decoder verifies the checksum before writing the output, detecting bit-rot or accidental truncation.

🎤 Interview-Ready Q&A

Why does your project use an 8 KB internal buffer in BitWriter and BitReader?
  • Each output.put() / input.get() is a system call that crosses the kernel/user boundary.
  • For a 2 MB compressed file there are over 1 million such calls — each stalling the CPU pipeline.
  • An 8 KB buffer reduces those to ~128 bulk write()/read() calls — a 99.99% reduction in system-call overhead.
  • 8 KB is chosen because it fits in L1/L2 cache, keeping memory access fast.
How does stored mode prevent negative compression (the archive being larger than the original)?
  • Before encoding, compute encodedBytes = encodedBits / 8 and huffmanOverhead = 2 + usedSymbols × 9.
  • If encodedBytes + overhead ≥ originalSize, write method = STORED and copy bytes verbatim.
  • The archive overhead is only the fixed HUF1 header (a few dozen bytes), never the Huffman frequency table.
What guarantees deterministic Huffman tree reconstruction at decode time?
  • When two nodes have equal frequency in the priority queue, the tie is broken by choosing the node with the smallest byte symbol value.
  • This is implemented via the smallestSymbol field propagated up through internal nodes.
  • Because the tie-breaking rule is the same at both encode and decode (only the frequency table is stored), the tree is always identical.
Why doesn't Huffman coding compress JPEG, MP4, or PPTX files?
  • These formats apply their own entropy coding (JPEG uses Huffman + DCT, MP4 uses H.264, PPTX is a ZIP archive internally).
  • After their own compression, the output bytes appear pseudo-random — every value 0–255 has roughly equal frequency.
  • Huffman can only exploit symbol imbalance; with uniform byte distribution it assigns ~8-bit codes to 8-bit values, giving zero gain.
How does the Python GUI know what filename to suggest when restoring a file?
  • The Python code opens the .huf archive directly and reads the first 18 bytes.
  • It validates the HUF1 magic and parses the 2-byte filename length at offset 16.
  • It reads that many UTF-8 bytes and strips the directory path with os.path.basename().
  • This happens in Python without invoking the C++ decoder, keeping the UI responsive.
What is the time complexity of building the Huffman tree?
  • O(n log n) where n is the number of distinct symbols (at most 256).
  • Building the initial heap: O(n). Each merge operation: O(log n) for heap push/pop.
  • Since n ≤ 256, this is effectively O(1) relative to file size. The dominant cost is the file I/O passes.
Why use std::unique_ptr<Node> for tree nodes?
  • Each node is heap-allocated; unique_ptr ensures automatic cleanup when the nodes vector is destroyed.
  • Raw pointers into the same vector are safe to use for child links because the vector is never modified after building.
  • This is RAII — the tree memory has a clear, deterministic lifetime tied to the huffman object.
Why does the decoder stop at exactly original_size bytes rather than at end-of-stream?
  • The last byte of the bit-stream may be zero-padded (up to 7 bits of padding).
  • Without knowing the original size, the decoder could emit extra bytes decoded from those padding zeros.
  • Storing originalSize in the header lets the decoder emit exactly the right number of bytes and stop — no end-of-stream sentinel needed.
How would you extend this project to support compressing an entire directory?
  • Introduce a new archive version (HUF2) with a multi-entry structure.
  • Each entry: sub-header (relative path, original size, method) followed by its payload.
  • The encoder recursively walks the directory with std::filesystem::recursive_directory_iterator.
  • The decoder reads entries sequentially, recreating the directory tree with std::filesystem::create_directories().
What would you add to make this production-grade?
  • Checksums: CRC-32 or SHA-256 of the payload to detect corruption.
  • Streaming interface: Process files larger than available RAM in fixed-size windows.
  • LZ77 pre-pass: Exploit repeated byte sequences (forming DEFLATE) for far better ratios on structured data.
  • Thread safety: Allow concurrent compress/decompress calls from different threads.
  • Progress callbacks: Expose a callback so the GUI can display a progress bar in real time.
